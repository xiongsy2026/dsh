> §8 视觉 token 与 §5 的 N≥4 tab 栏**已落**；展示清单 5 条（超级复刻 / Hypit 视频裂变 / Omni 出片 / 短剧 agent 带货 / 视频去水印）：前 4 张封面是**临时候选**，第 5 条**故意还没封面**（走首字母兜底·见 §8.5 登记表）。

关键前提（2026-10-01 写的，现已过时但规则保留）：当时只有 1 个技能，设计必须**按技能数自适应**，不能为 1 个技能摆一排空 tab / 空轮播。

## 1. 目标
新对话页（输入框下方）让客户一眼看到"你能让我做什么"，点一下就调用对应技能。随技能数量增长，形态从"单卡/引导行"平滑升级到"tab + 轮播"。

## 2. 非目标
- 不做"本周热门"这类 **trending**（1.0 无跨用户后端统计，做不了）。
- 不改 DSH 内核；不新建插件 bundle（复用已加载的 super-clone-ui）。
- 不自动发消息（点击只填输入框，客户补需求）。
- 🔴 **不做"对话中的技能条"**（2026-10-04 用户定）：这块只在**新会话首页**出现，一旦进入对话就整块撤掉。

## 3. 技术落点（已扒 bundle 坐实）
- 宿主：`plugins/super-clone-ui`（已是 `apply(ctx)` 形态、已加载、拥有主题 token）→ 改它的 client.js + 重启，**零新插件部署链**。
- 挂载槽：**`conversation.composer.dock`**（官方契约"Ambient entries below the composer card"，scope:session）。
  ⚠️ body 的 props 实测是 **`{ session, input }`**（`dsh-client-ui-conversation/lib/client.js:14855` 的 `extensionZone`），
  **没有 `sessionId` 这个键** —— 读 `props.sessionId` 恒为 `undefined` ⇒ 上游直接 `session/not-found`、整块静默不渲染。
  会话 id 走 `props.session.sessionId`（`inputActions` 由 session scope 合并注入，这个才有）。
- 技能来源：`ctx.remote.skills.list({sessionId}, signal)`。⚠️ 它回的是 **Remote 信封** `{ok, value:{skills}, error}`，
  **不是数组**（内核 `dsh-client-ui-skill/lib/client.js:253-255` 就这么拆）；把返回值当数组 = 恒空 = 一条卡都不出。
- 点击调用：`props.inputActions.setDraft("/<skill> ")`（原生 `/` 选择器也只是插这段文本，无 skills/invoke RPC）。
- 皮肤：全用 `var(--dsw-alias-*)` → 自动跟 Weeksir 橙主题（`--dsw-alias-brand-primary:#fa6f08`）、明暗自适应。

## 4. 数据模型（和路由 PRD 合流，一份元数据喂两处）
每个 `SKILL.md` frontmatter 的 `display` 块：
```
display: { title, tagline, cover, order, collections: ["reco"] }
```
- `title`/`tagline`/`cover`：卡片展示。cover 缺 → 首字母 + 橙渐变占位。
- `order`：推荐清单里的排序（策展权重）。
- `collections`：归属分组（`reco`=推荐；未来 `video`/`image` 等分类）。
- 路由用 `whenToUse/whenNot`，展示用 `display`，同一份文件。

## 5. 自适应设计（核心，回应"才 1 个技能"）
按**可见技能数 N** 决定形态：

| N | 形态 |
|---|---|
| **0** | 整块隐藏（不占位）。 |
| **1** | **不摆 tab、不轮播**。就一个"能力卡"（封面+名+一句 tagline+「去使用 ›」），或退化成一行引导："你可以让我做 —— Omni 出片 ›"。目标是**不显得空**。 |
| **2–3** | 一行卡片（无 tab），超出可横滚。 |
| **≥4** | 上 **tab 栏**（`最近使用 / 推荐技能`）+ 单卡片区轮播（左右箭头）。 |
| 未来 | tab 位扩展成分类（视频/图片…）；trending 待有后端再加。 |

→ **P0 只做 N=1 的形态**（当前就 1 个技能），代码里按 N 分支预留 2–3 与 ≥4，技能加够了自然升级，不用重写。

## 6. Tab 逻辑（仅 N≥4 启用）
- **推荐技能**：运营策展的**有序清单**（按 `display.order`），不是 `skills.list` 原序。
- **最近使用**：本地记录点过的技能（`localStorage`，最近优先、去重、上限 8）；**空则该 tab 不显示**（首次只"推荐技能"）。
- 两者允许重叠（不剔除）。默认选中"推荐技能"。

## 7. 交互
- 点卡片 → `setDraft(当前草稿 + "/<skill> ")` 填进输入框、光标停那、**不自动发**；同时写入"最近使用"。（`setDraft` 是**整体替换**，不带当前草稿会把客户已打的字冲掉。）
- **出现范围**：仅首页。判据照内核那条 hero 规则（`dsh-client-ui-conversation:14775/14854`，字段来自 session 快照 `session.js:720-736`）：
  `session.blank === false`（已有内容）/ `running` / `promptAttempted`（首轮已提交）任一成立 ⇒ 整块撤，且**不再发 `skills.list`**。
  内核还看了 `activeTargets` 与 `openState`：前者是会话内浮层、dock 拿不到也不该拿；后者只影响 settling 一帧，为它让卡片闪进闪出不值，都没抄。
- 卡片 hover：上浮 + 橙描边 + 阴影。
- 空态（N=0 或最近为空）：不显示 / 一行小灰字引导。

## 8. 视觉 token（对齐小云雀架构、皮肤用 DSH）
- 卡片：圆角 12px、`--dsw-alias-bg-layer-1` 底、`--dsw-alias-border-l1` 描边；封面区 ~132px 高、底部文字叠层（标题 14/20、描述 12/17）。
- **纵向节奏（2026-10-04 两轮实屏调定）**：输入卡 → **18px** → tab 行（箭头与 tab 同排，左右两端）→ **6px** → 封面。
  两段各有各的值，别合成一段：tab 离封面远了像两块东西，离输入卡太近又贴不住"这是输入框下面的推荐"。
- 强调 `--dsw-alias-brand-primary`（橙）；hover 上浮 3px + 阴影。
- 参考小云雀**只借结构**（tab + 图卡轮播），不套它的紫/玻璃。

## 8.6 封面画面设计（按功能逐张定稿 · 2026-10-04）

> 上一版的问题复盘（写死防复发）：5 张各自一个 prompt ⇒ 底色/构图/主体语言全不同，摆一排像 5 个来源；
> 且 3 张主体都是白鞋（没为各技能想"它的画面特征是什么"）；去水印那张更是在**链路从没真跑过**的情况下画概念图。
> 规矩：**先定"这个能力在画面里是什么动作"，再谈出图**；没有真实依据的能力（未跑通的腿）宁可首字母兜底。

### 统一视觉系统（5 张必须像一家）
| 项 | 规定 |
|---|---|
| 底 | 同一深炭色底，主体外大面积留负空间 |
| 主体 | **单一产品或单一动作**，居中偏左，占画面高 55–65% |
| 品牌橙 | 只做**一条光带 / 一个高亮点**，禁止大色块（橙色块会抢产品） |
| 底部 | 25% 高度留给叠字，**由后期统一压暗渐变**保证可读，不靠 prompt 描述颜色 |
| 构图 | 16:9，四周留安全区；输出 472×264（236×132 @2x） |
| 禁字 | 🔴 prompt 里**不出现任何字面量**（连 `16:9` 都不写——上次模型把它照抄进画面了）；比例走脚本参数。出图后**人眼过一遍**，有字就本地裁/糊（0 花费），不许带字登记 |
| 商标 | 画面里不许出现可识别的第三方商标（v2 那双 AF1 的 swoosh + 中底"AIR" 就是这么被刷掉的） |

### 逐张画面（功能 → 画面动作）
| 技能 | 这个能力的动作是什么 | 封面画面 | 为什么读得出来 |
|---|---|---|---|
| **super-clone 超级复刻** | 拿爆款原片，**只换商品身份**，运镜/动作/口播节奏锁死 | 同一机位、同一背景、同一光位的**两个画面左右并置**，中间一条细光缝；左：原片商品（素色保温杯），右：**同位置换成另一个产品** | "同一条片子，产品被换掉"是复刻的全部语义；旧图只放一只鞋 = 没有替换感（登记表里我自己标过这条） |
| **hypit-pipeline 视频裂变** | 一条参考视频 → **语义重建成多段**、可分裂成多版本，代码化编排 | 深色底上一排**横向胶片格（6 格）**，其中一格正在**一分为二**；格子之间用纯几何细连线表示编排（不写字、不做代码字符） | "裂变"直读=一格变两格；连接线承担"工程化"的暗示，避免画真代码（画必乱码） |
| **omni 出片** | **一张产品图 → 一条竖屏广告片**（剧本→关键帧→运镜→拼接） | 左侧一张**方形产品照卡片**（无品牌白瓷杯），右侧一个**竖屏 9:16 画框**，框内是带运动模糊与雾环的动态帧，中间一道橙色光箭头 | 输入→输出的形态差（方图 vs 竖屏动态）就是这条能力的说明书 |
| **short-drama 短剧带货** | **剧情冲突承载卖点**，八阶段链路推理出可生成提示词 | 两人隔桌**对峙**的戏剧帧，中间**一件小商品被一束光托起**成为矛盾焦点；画面下沿一排 **8 个小节点**表示八阶段（纯几何点，不编号不写字） | 旧图方向对但产品不在焦点上；"谁在争什么"一眼看到产品 = 剧情带货的定义 |
| **video-dewatermark 视频去水印** | 一条已生成视频，**清掉平台文字/图标**，画面本身不动 | **同一帧左右半幅对比**：左半浮着若干**半透明圆角矩形**（抽象水印块，绝不用字符），右半干净；中间一道竖向擦除光带 | 唯一诚实的画法就是 before/after；主体换成无商标素色产品（沿用被刷掉的 v2 构图，换掉那双 Nike） |

### v3（真实帧）为什么废掉 —— 以及 v4 的定稿依据
v3 试过"主体一律用我们自己成片的真帧 + 借小云雀的机制画法"，逐格人眼过完素材后**否掉了**：
盘上真跑出来的素材要么**带真人**（复刻原片里是真人女性、袜子参考片是真人主播 + 中文硬字幕），要么是**白底产品图**（软糖生成帧），
拼出来像"白底器物 + 贴纸符号"，比 v2 还没大片感。⇒ 结论写死：**我们的历史素材不足以当封面**，别再用它凑。

从小云雀三张卡（3D导演台=半线框车身 / 智能预演=一排片段缩略 / 超分=左右擦除+放大镜）真正学到的两条，v4 一起用了：
① **机制画进画面里**，但用场景内的光与物体表达，不贴几何符号；② **主体必须在环境里** + 电影打光（anamorphic、体积雾、青橙调、颗粒），满幅不留大片负空间。

## 11. 技能管理与自动化更新（分发架构）
每个技能会持续迭代；客户拿到客户端后，技能更新**不该**要求重装整个 App。分阶段：

- **1.0（本地·自用，现状）**：技能在本地 `.dsh/skills/`。更新=你直接改文件（或 `git pull` 一个 skills 仓库）。**没有客户，先不做更新机制**。
- **过渡（发客户端包）**：技能打进 Electron 包 → 更新技能=发新包（App 自动更新器）。重、慢，只适合已稳定的技能，不适合频繁迭代。
- **3.0（瘦客户端 + 服务端，正解）**：**技能住服务端**（agent 在服务端跑），客户端只渲染对话/右栏。→ **更新技能 = 改服务端一处，所有客户下次会话自动拿到，零 per-client 更新**。这才是"客户自动化更新"的根治，且天然解决密钥/版本/多租户（见 [[dsh-product-roadmap]] [[dsh-client-release-shaping]]）。

**中间态（若某阶段技能必须留在客户端）**才需要远程更新机制，最小设计：
- **manifest**：`{skill_id → version, checksum, min_client_version, visibility}`，托管在 CDN/Git。
- 客户端启动/定时比对 manifest → **只下载变化的技能包** → 校验 checksum → **原子替换** → 保留 **last-good 可回滚** → 离线用缓存版。
- **兼容**：技能声明 `min_client_version`，不匹配则不下发/不启用（防新技能跑在旧客户端上崩）。
- **安全**：技能包**签名**、**绝不含密钥**（密钥走服务端，见 [[model-gateway-direction]]）；按账号/套餐控制 `visibility`（客户只看该看的技能）。

**统一元数据的好处（和路由/展示合流）**：技能只有一份 `SKILL.md`（含 `version` + `display` + `whenToUse`）。更新它 = 路由、展示 dock、执行**同时**生效，不用三处维护。→ 现在就给每个 SKILL.md frontmatter 加 `version` 字段，为将来更新/兼容打底。

**决策建议**：1.0 **不建更新基础设施**（过度工程，契合 [[feedback-keep-simple]]）；只给技能加 `version` 字段占位。真正的自动更新留到 3.0 服务端模型，届时近乎免费。是否要我把"给每个 SKILL.md 加 `version` 字段"列进 P0？
